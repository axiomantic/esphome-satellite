# AGENTS.md - Developer & Agent Guide for esphome-satellite

This document outlines architecture invariants, workflows, and audio processing pipelines for human contributors and AI agents working on `esphome-satellite`.

---

## 1. Repository Architecture

- **`src/`**: Nim implementation and C ABI bridge layer for ESPHome.
  - `nim_esphome_satellite.nim`: Main Nim integration module compiling state machines, audio DSP, and hardware routines into a single translation unit.
  - `audio_dsp.nim`: Real-time speech compression, makeup boost, and soft-limiting audio DSP in Nim.
  - `xvf3800_hardware.nim`: XMOS XVF3800 GPO control and 12-LED ring animation engine in Nim.
  - `wake_partition_loader.nim`: Dynamic microWakeWord loader and header validator in Nim.
  - `pcm_sound_player.nim`: Zero-heap IMA-ADPCM decompression and WAV header parser in Nim.
  - `pcm_sound_player.h`, `wake_partition_loader.h`, `xvf3800_hardware.h`: Minimal C++ adapter bridges delegating to Nim C ABI entry points.
  - `sound_data.h`: Auto-generated byte arrays containing 51 pre-compiled sounds (17 Wake Chimes, 17 Processing Loops, 17 Cancel Sounds).
- **`packages/respeaker_xvf3800.yaml`**: Main ESPHome package definition with typestates, micro_wake_word, and Home Assistant entities.
- **`scripts/`**: Automation tooling for audio processing, web installer generation, and firmware builds.
- **`web/`**: Static site hosted on GitHub Pages for WebSerial browser flashing.

## 2. Nim-First Architecture Policy & C/C++ Interop

All new features, hardware drivers, audio DSP pipelines, state machines, and business logic must be implemented in **Nim**.

### Invariants:
1. **No Custom C++ Logic**: Custom algorithms, state machines, and peripheral control must not be written in C++. The only acceptable C++ files are upstream forks (e.g. `components/i2s_audio`) and the thin C ABI adapter bridges.
2. **nim-esphome Wrappers**: Use the standard wrappers provided by `nim-esphome` (`nim_esphome/i2c`, `nim_esphome/gpio`, `nim_esphome/dsp`, `nim_esphome/entities`, `nim_esphome/dsl/actions`).
3. **Automated C/C++ Binding Generation with headerkit**:
   When wrapping C or C++ third-party libraries or ESP-IDF / ESPHome headers, use `headerkit` (installable via `pip install headerkit`) to automatically parse headers and emit clean Nim FFI bindings rather than hand-writing raw externs.
4. **Single Translation Unit via Nim Include**:
   Nim submodules integrated into the ESPHome firmware build should be included (`include <module>`) within the root `src/nim_esphome_satellite.nim` translation unit. This guarantees that all procs and global state compile directly into `@mnim_esphome_satellite.nim.cpp.o` without unresolved module initialization symbols (`at<module>dotnim_Init000`) during the PlatformIO link step.
5. **Strict Test-Driven Development (TDD)**:
   Every Nim module must have dedicated unit tests in `tests/`. Always perform anti-green-mirage verification (deliberately mutate logic to verify tests fail with exact diagnostics before finalizing).

## 3. Audio Processing Pipeline & Adding New Wave Files

Every audio file included in `esphome-satellite` must pass through the standardized audio processing pipeline before inclusion.

### Why Transcoding, Normalization & Compression Are Required
Voice satellites operate on small onboard speakers (1W to 2W) with limited dynamic range and low amplifier headroom:
- **Uncompressed audio** causes physical speaker rattle and distortion during loud transients (e.g. sharp bell strikes).
- **Inconsistent volume** means one theme sounds inaudible while another is deafening.
- **Sample rate mismatches** cause pitch distortion or buffer overflows.

### The Audio Pipeline Script
Run the pipeline whenever you add, replace, or tune `.wav` audio files:

```bash
# Via Python (uses ffmpeg)
python3 scripts/process_audio.py

# Or via Nim
nim c -r scripts/transcode_sounds.nim
```

### What the Pipeline Does
1. **Format Enforcement**: Resamples all audio to 16,000 Hz mono 16-bit PCM.
2. **Light Dynamic Range Compression**:
   - Filter: `acompressor=threshold=-12dB:ratio=2.5:attack=5:release=80:makeup=1.5dB`
   - Clamps harsh transient spikes while lifting soft harmonic tails.
3. **Peak Normalization**:
   - Normalizes audio to `-1.0 dBFS` true peak to guarantee uniform volume across all 17 acoustic themes without DAC clipping.
4. **Seamless Loop Preservation**:
   - Looping processing sounds (such as `clockwork.wav` at 32,915 samples) retain their exact mathematical sample counts for zero-gap looping.
5. **Asset Sync & Web Preview**:
   - Writes 16-bit PCM `.wav` files to both `assets/sounds/` and `web/sounds/`.
   - Transcodes 128kbps `.mp3` previews using `libmp3lame` for the in-browser Audio Showcase.
6. **Sound Bank Compilation**:
   - Encodes all audio to IMA-ADPCM (4:1 compression ratio, ~333 KB total).
   - Re-generates `src/sound_data.h` including `STEP_SIZE_TABLE`, `INDEX_TABLE`, and `find_sound()`.

## 4. Custom Audio Transcoding: Nim vs. TypeScript

When users provide **custom audio**, transcoding should occur depending on the context:

### A. End-User Browser Uploads: TypeScript (Web Audio API)
- **Where**: In the Web Installer (`web/index.html` via `nim-esphome/dsl/installer.nim`).
- **Why TypeScript / Web Audio**:
  - End users flashing via WebSerial cannot run local CLI tools (no Python, Nim, or FFmpeg installed).
  - The browser's native **Web Audio API (`OfflineAudioContext` + `DynamicsCompressorNode`)** runs entirely client-side on any desktop browser.
  - It decodes any input container (`.mp3`, `.wav`, `.m4a`, `.ogg`, `.flac`), resamples to 16kHz mono, applies compression and normalization, and packs the bytes into the binary format before flashing to the ESP32 partition.

### B. Repository & CI Builds: Nim / Python CLI Script
- **Where**: `scripts/process_audio.py` / `scripts/transcode_sounds.nim`.
- **Why**:
  - Offline batch processing of repo assets in CI and during local development.
  - Automates header generation (`sound_data.h`) and MP3 previews.

## 5. Verification & Release Checklist

After modifying audio, firmware, or installer logic:

1. **Process Audio** (if modifying .wav audio files):
   ```bash
   python3 scripts/process_audio.py
   ```
2. **Automated Web Binaries via CI (No Manual Commits Required)**:
   Do not manually build or commit factory binaries (`firmware-factory.bin`, `firmware-ota.bin`). GitHub Actions automatically builds the factory binaries on push to `main`, stamps `web/version.json` and `web/manifest.json` with the git commit SHA and build timestamp, and commits them back to the repository. If you need to test the build locally:
   ```bash
   bash scripts/build_factory_binary.sh
   ```
3. **Regenerate Web Installer** (if modifying scripts/generate_web.nim):
   ```bash
   nim c -r scripts/generate_web.nim
   ```
4. **Run Invariant Tests**:
   ```bash
   nim r tests/test_fsm.nim
   nim r tests/test_version_sync.nim
   nim r tests/test_audio_dsp.nim
   nim r tests/test_xvf3800.nim
   nim r tests/test_wake_loader.nim
   nim r tests/test_pcm_player.nim
   ```
5. **Style Guidelines**:
   - **Zero Emojis**: Never use emojis in documentation, READMEs, HTML pages, commit messages, or PR descriptions. Keep all prose clear, technical, and human.
6. **Commit and Push Invariant**:
   - All changes must be committed and pushed once reviewed. Implementations and fixes are never left uncommitted in the working tree or unpushed to the remote repository. Always rebase on the latest remote before pushing.
